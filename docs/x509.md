# X.509-SVIDs

An issuer with a certificate authority (CA) hands out X.509-SVIDs next to JWT-SVIDs: short-lived
certificates that name a workload by its SPIFFE ID, for mutual TLS between services and for data
stores that authenticate clients by certificate. The identity is the same one a JWT-SVID would have
carried, decided by the same origins, providers and naming; only the kind of document differs.

This guide is the whole path: what the certificates look like, how to set up and rotate the CA,
what to do when a key leaks, how workloads and data stores use the certificates, and what has and
has not been tested. [SPEC.md](../SPEC.md) (sections 2.5, 3.4, 4.5 and 7.2) says what an
implementation must do, and [Configuration and operations](configuration.md) has every setting and
flag. A CA is optional: an issuer without `ca_dir` behaves exactly as it did before and issues
JWT-SVIDs only.

## What an X.509-SVID looks like

For `spiffe://example.org/prod/ns/shop/sa/billing`, issued by a CA that `spiffex ca init` made:

```text
Subject:   O=example.org, CN=spiffe://example.org/prod/ns/shop/sa/billing
Issuer:    the signing CA's subject, byte for byte
Not Before: the time of issue minus 30 seconds
Not After:  the time of issue plus x509_svid_ttl (one hour by default), or earlier, see below
Subject Alternative Name: URI:spiffe://example.org/prod/ns/shop/sa/billing
Basic Constraints (critical): CA:FALSE
Key Usage (critical): Digital Signature   (and Key Encipherment for an RSA key)
Extended Key Usage: TLS Web Server Authentication, TLS Web Client Authentication
```

- **The identity is the URI SAN.** There is exactly one name, a URI, and no DNS name, IP address or
  email. A verifier takes the SPIFFE ID from there and from nowhere else, as the [X.509-SVID
  standard](https://github.com/spiffe/spiffe/blob/main/standards/X509-SVID.md) requires.
- **The subject repeats it for programs that cannot read a SAN.** PostgreSQL, MariaDB and Valkey map
  a client certificate to a user by its common name or subject, and none of them looked at a URI SAN
  until recently. So the issuer sets `O` to the trust domain and `CN` to the full SPIFFE ID. Each is
  left out when it is longer than 64 characters, the limit in RFC 5280, and never truncated: two
  identities then never share a CN, and a data store that matches on it refuses the long one instead
  of confusing it with another. So a workload that must authenticate to a data store matching on the
  CN needs a SPIFFE ID of 64 characters or less, or an origin that chooses a shorter CN with
  `x509.cn` ([below](#choosing-the-common-name)). When both are left out the SAN is marked critical,
  as RFC 5280 says. Path segments cannot contain `/`, `,`, `=`, `+` or `\`, so the subject reads the
  same in every common rendering. Nothing in the subject comes from the workload's request.
- **Both key usages for TLS are set.** An X.509-SVID can authenticate a client and a server. It
  carries no DNS name, though, so a client that checks the server's host name (libpq's
  `verify-full`, a browser) cannot use it as a server certificate. Servers reached by name keep a
  certificate for that name.
- **The lifetime is short and cannot be revoked.** The default is one hour, between 10 minutes and
  24 hours (`x509_svid_ttl`). An issued certificate stays valid until it expires, wherever a removed
  origin or member goes. The issuer logs every certificate with its serial number, SPIFFE ID, origin
  and expiry, at every log level, because that log is the only record.
- **The chain.** The token endpoint and the agent hand out the leaf first and, for a CA that is an
  intermediate, the intermediate and anything between it and the root after it. The root itself is
  never sent: it is in the trust bundle, which verifiers fetch from the issuer's bundle endpoint or
  through the agent. `notAfter` is cut short where the chain ends sooner than a full lifetime, and
  the issuer refuses to issue when fewer than five minutes would remain.
- **Only the public key comes from the workload.** The request carries a CSR, and the issuer uses
  its public key and nothing else: P-256, P-384, Ed25519, or RSA of 2048 to 4096 bits. The signature
  on the CSR proves the workload holds the key. A key the issuer already uses as a CA, JWT signing
  or member key is refused.

## Setting up the CA

Set `ca_dir` in the settings to a directory of its own, apart from `keys_dir`. There are two shapes.

**A root made by spiffex**, for development and small setups. The issuer is the trust domain's root
of trust and its certificate is the one trust anchor:

```bash
spiffex ca init -dir /var/lib/spiffex/ca -trust-domain example.org
```

The root is a P-256 key valid for five years (`-valid-for`). Nothing renews it, so add its successor
well before it ends; the issuer warns from 30 days out.

**An intermediate under your own root**, the better production setup, because a root kept offline
can replace a compromised intermediate and a root made by the issuer cannot. The key is made on
the issuer's side, the request signed on the machine that holds the root, and the answer installed:

```bash
spiffex ca csr -dir /var/lib/spiffex/ca -trust-domain example.org -out ca.csr
# on the machine with the root: sign ca.csr as a CA certificate, name-constrained as below
spiffex ca import -cert signed.pem -dir /var/lib/spiffex/ca -trust-domain example.org \
  -roots /etc/spiffex/ca-roots.pem
```

`ca_roots` names a PEM file with your root certificates. Those are what the bundle publishes, not
the intermediate. `ca csr` takes `-alg ES384` or `-alg RS256` for an intermediate whose key type
your root's policy dictates. `ca import` takes the signed certificate first and any CA
certificates between it and the root after it, and checks them against the profile before it
writes anything.

**The name constraints are what limit a stolen CA key.** A CA certificate carries a critical
`nameConstraints` extension that permits only the URI `example.org` and excludes subdomain URIs
(other trust domains), every DNS name, IP address and mailbox. A verifier that enforces the
constraints then rejects any certificate the CA signs for another trust domain or for a host name,
whoever holds the key. `ca init` and `ca csr` ask for exactly this; a CA is free to ignore the
request, so `ca import` and the issuer check what comes back. The extension has no directory name
constraints, on purpose: Go refuses a CA with a critical one, and OpenSSL would apply an excluded
one to every leaf's subject.

**`ca_roots` and `ca_roots_dedicated`.** The issuer cannot see the other CAs your root certifies,
and a verifier that trusts the root accepts `spiffe://example.org/...` from any chain that ends in
it. So every root in `ca_roots` must either carry the full name constraints above or be declared
dedicated to this trust domain with `ca_roots_dedicated: true`, which is your statement that
every CA the root certifies is one of this issuer's signing CAs or on the path to one. The issuer
refuses to start with a root that is neither. Even the full constraints do not stop a sibling CA
under a shared root from minting identities of this trust domain, so share a root only with CAs
that are yours.

The settings, rereading rules, files in `ca_dir`, and the checks the issuer runs are in [The
certificate authority](configuration.md#the-certificate-authority). With Helm the CA is a Secret
(`ca.existingSecret`) and the roots a ConfigMap or Secret (see the [chart's
README](../charts/spiffex/README.md#the-certificate-authority)).

## Rotation

Rotation follows the rules of the JWT signing keys, applied to the trust anchors:

- **Activation delay.** A new anchor is published in the bundle for `activation_delay` (30 minutes
  by default) before the issuer signs with anything that chains to it, so that verifiers have
  fetched it. The exception is a CA with a key when no other CA can sign, as in a new trust domain
  or after the only CA key was removed: it signs at once. The delay counts from when the running
  issuer first sees the certificate, not from its file name or dates. A new intermediate under a
  root that has been published that long signs as soon as it appears. When several CAs may sign, the
  newest does.
- **Retention.** An old anchor stays published until `x509_svid_ttl` plus ten minutes after the last
  time it could have signed, so that nothing it issued stops verifying early. This holds for files
  that are still in place. A certificate you delete leaves the bundle at the next reload, with no
  retention, unless a CA that still has its key chains to it, in which case it stays. A root removed
  from `ca_roots` behaves the same way. If the `ca_roots` file itself cannot be read, the issuer
  keeps the roots it had, so edit that file rather than delete it.
- **Prune.** `spiffex ca prune -config issuer.yaml` deletes the files of CAs no verifier can need
  any more, and `-dry-run` shows what it would delete. `ca list` shows each CA and anchor and which
  signs. Run them against the directory the issuer reads, after the retention has passed there.
  Prune removes only CAs that still have a key; it leaves certificates without a key alone, so
  delete those yourself.

To replace a root: run `spiffex ca init` and wait for `activation_delay` (it then signs), or add the
new root to `ca_roots`, wait, and install an intermediate under it. Then wait out the retention,
then `ca prune` and remove the old root from `ca_roots`. Under an intermediate you rotate the same
way with a new intermediate signed by the same root, and no anchor changes. Do not restart the
issuer within `activation_delay` of adding a root, since it keeps no memory of what it first saw
([the details](configuration.md#the-certificate-authority)).

The kind test in `test/e2e/kind-x509.sh` rotates the CA with two pods holding a connection and
checks that the connection is not dropped and that new connections use the new CA.

## When a key leaks

An X.509-SVID cannot be revoked and a JWT-SVID lives for minutes, so the response is to stop the
issuer signing with the key and to make verifiers forget it. Removing a file does both: the
issuer rereads its directories every `-reload-interval` (10 seconds by default) and verifiers
pick up the new bundle within `spiffe_refresh_hint`.

**A CA key.**

1. Delete the CA's `.key` file. A CA certificate without a key never signs, so signing with it stops
   at the next reload. The certificate stays published, so what it already issued still verifies.
2. Bring in a replacement, as in "Rotation". If another CA with a key is in service, it goes on
   signing and the new one waits out `activation_delay`. If none is left, the new CA signs at once,
   as in a new trust domain, since waiting would only add an outage. Its root is published in the
   same moment, but verifiers that already hold the bundle reject what it signs until they fetch the
   bundle again: agents and other bundle-endpoint consumers within `spiffe_refresh_hint`
   (`activation_delay`/5, 6 minutes by default), and consumers that read a bundle file when they
   reread it. An agent and `spiffex token -x509` fetch the bundle again themselves, so the
   workload's own certificate and bundle always agree; it is the peers that may refuse it for that
   long. To shorten the window, lower `activation_delay` ahead of time; the refresh hint is a fifth
   of it. A ready intermediate under an anchor that has been published long enough signs at once,
   and verifiers already accept it.
3. To stop trusting what the leaked key can still mint, remove the anchor it chains to. For a
   self-signed root, delete the root's certificate. Under an offline root, remove that root from
   `ca_roots`, even when only the intermediate leaked: the bundle holds roots, not intermediates,
   and there is no revocation list, so one intermediate cannot be distrusted on its own. Until
   verifiers have fetched a bundle without that root, a thief holding the intermediate's key can
   mint X.509-SVIDs that verify, but only until the intermediate's own `notAfter`, because verifiers
   check every certificate in the chain. The exposure ends when the root leaves the bundle or the
   intermediate expires, whichever comes first. The name constraints keep those SVIDs to this trust
   domain's URIs, and the path length of 0 keeps the thief from making a CA. Plan for this when you
   pick a lifetime for the intermediate. The replacement must chain to a different root, and every
   intermediate with a key under the old root must be gone from `ca_dir` first: the issuer keeps
   publishing a root that a CA in service still chains to.
4. Delete the leaked CA's certificate file by hand: `ca prune` removes only CAs that still have a
   key and whose retention has passed, and a certificate left without its key keeps logging a
   warning. Wait `activation_delay` before restarting the issuer, since a restart forgets how long
   an older CA's root has been published.

Removing the key of the last CA leaves the issuer running. It goes on publishing the anchors,
signs no X.509-SVIDs and leaves JWT-SVIDs alone, and discovery drops
`spiffex_x509_svid_supported` until a CA can sign.

**A JWT signing key.**

1. Delete the key's file from `keys_dir`. Any other key in `keys_dir` signs at once, the newest one
   past its activation delay if there is one. Verifiers fetching the JWKS or the bundle stop
   accepting tokens the key signed; agents drop the cached JWT-SVIDs of a key that has left the
   bundle when they next refresh it.
2. If it was the only key, the issuer stops signing JWT-SVIDs rather than keep a leaked key. This is
   confirmed by a second poll that also finds no key, so an editor that renames the file away and
   back, or a volume remounting, does no harm; the response therefore takes up to two reload
   intervals. The issuer logs an error and keeps running: the token endpoint answers a JWT request
   with `invalid_request` ("this issuer issues no JWT-SVIDs"), the JWKS and the bundle publish no
   JWT key, discovery still lists ES256 and RS256, the agent sends its workloads an empty JWT
   bundle, and the management API admits nobody, since it can neither mint nor verify a management
   token. X.509-SVIDs are unaffected.
3. `spiffex key add` makes the replacement. With no other key it signs at once, as in a new trust
   domain. With another published key it waits out the activation delay as usual.

Nothing is kept for a removed key: removal is the revocation. An issuer that starts with an empty
`keys_dir` and has a CA behaves the same way, so the response survives a restart; one without a CA
refuses to start with nothing to publish.

## Which origins get X.509-SVIDs

`svid_types` on an origin, or on a provider as the default for its origins, is a non-empty list of
`jwt` and `x509`. The origin's list replaces the provider's. When neither sets one, an origin gets
both, so turning on a CA gives every origin X.509-SVIDs. A request for a kind the list lacks
fails with `invalid_target` after authentication, and the agent passes that on as
`PermissionDenied` to the workload.

<!-- check: state -->
```yaml
origins:
  prod:
    provider: kubernetes
  ci:
    provider: github
    with: { owner_id: "1234567", refs: [refs/heads/main] }
    svid_types: [jwt]
```

Here `prod` gets both kinds and `ci` only JWT-SVIDs. A shared upstream whose identities should not
authenticate to every server that trusts the bundle is the usual reason to write `[jwt]`: an
X.509-SVID has no audience, so any server that trusts the bundle accepts it until it expires.
For the same reason an origin with an `audiences` restriction defaults to `[jwt]`, and listing
`x509` on it is allowed but discouraged, because the restriction then does not apply to its
certificates. `spiffex check` and `POST /manage/check` report such origins
(`x509_under_restriction`).

## Choosing the common name

By default the CN is the whole SPIFFE ID, which leaves 26 characters for the part after
`spiffe://example.org/tenants/` in PostgreSQL's 64-character CN. `x509.cn` on an origin, or on a
provider as the default for its origins, is a template that chooses the CN instead. It is literal
text around exactly one placeholder:

| Placeholder | Value, for `spiffe://example.org/tenants/kokkenogco/backend` |
|---|---|
| `{spiffe_id}` | `spiffe://example.org/tenants/kokkenogco/backend` |
| `{path}` | `/tenants/kokkenogco/backend` (a CN may not start with `/`, so use it with `trim_prefix:/`) |

Both come from the SPIFFE ID that was issued, never from the workload's token: a CN must name one
identity, and a CN built from claims could give two identities the same name. The placeholder takes
the operations of name templates, `trim_prefix:<text>` and `trim_suffix:<text>`, which refuse an
identity they do not apply to, and `hash:<n>`, which replaces the value by the first n characters (24
to 52) of the lowercase base32 of its SHA-256 and must come last. The text around the placeholder
and the arguments of the trims use `A-Z a-z 0-9 . _ - / :` only.

<!-- check: state -->
```yaml
origins:
  tenants:
    provider: kubernetes
    prefix: /tenants
    x509: { cn: "tenant:{path|trim_prefix:/tenants/}" }
  batch:
    provider: kubernetes
    prefix: /batch
    x509: { cn: "{path|hash:24}" }
  web:
    provider: kubernetes
```

Here `tenants` gives `tenant:kokkenogco/backend`, `batch` gives 24 characters of `a-z 2-7` and `web`
keeps the SPIFFE ID. The CN must come out at 1 to 64 characters. If it does not, because a trim does
not apply to an identity or the name is too long, the request fails with `invalid_request` and the
issuer logs which origin and identity, rather than issuing a certificate without the CN the origin
asked for. `spiffex check` refuses a template that can never work for its origin (a trim that never
applies, a CN that is always too long).

**Two origins cannot share a CN.** `spiffex check` and the issuer refuse a state in which two origins
that issue X.509-SVIDs could issue the same CN, because a data store that maps CN to role would then
treat them as one. Within an origin the template is one-to-one, as a hash is up to collisions of at
least 120 bits. Between origins the check proves that the names cannot meet, or refuses the state:

- `{path|trim_prefix:/}`, `{spiffe_id}` and the default are always fine next to each other, as
  origins' prefixes do not overlap.
- `{path|trim_prefix:/tenants/}` on the origin with prefix `/tenants` is fine next to those, since
  what is left starts with a name and the others start with `/` or `spiffe:`.
- Two origins that both trim their own prefix are refused (`/a/x` and `/b/x` would both be `x`), and
  so is a trim next to a hash (a tenant could be named like the hash of another identity). Give
  each origin's template text of its own, as `tenant:` above.
- Hashes of the same length and text are fine when their inputs differ, which `{path|hash:24}`
  always does; hashes of trimmed paths need text that differs, like trims do.

The check is conservative: it refuses a pair when it cannot show they are apart, even if in practice
they would be. A trim of a suffix is the usual cause; put distinct text first.

**A CN never starts with `/`.** PostgreSQL reads a `pg_ident.conf` system user that starts with `/`
as a regular expression, even in quotes, and not anchored: a line for `/tenants/x/backend` also
admits a CN `/zz/tenants/x/backend`. This was reproduced against PostgreSQL 15 and 16. So `spiffex
check` refuses a template whose names can start with `/` (`{path}` alone, `{path|trim_suffix:...}`,
text starting with `/`), and the issuer refuses to issue one. Use `{path|trim_prefix:/}` or put text
first, as `pg:{path}`. The default CN, the whole `spiffe://` ID, is not affected. Do not write regular
expression lines for these CNs: map each CN with a plain quoted entry that does not start with `/`.
If a regex is unavoidable it must be anchored and escape every metacharacter, `.` included, since
segments may hold dots; `^...$` alone is not enough (`.` would match `-`).

**Changing templates takes one lifetime.** Uniqueness is checked for the state as it is now. After you
change an origin's template, or give a name shape to another origin, certificates already issued with
the old names stay valid for up to `x509_svid_ttl`, one hour by default. Wait that long before mapping
a freed name to a different role.

`x509.cn` on an origin whose `svid_types` lacks `x509` is allowed and never applies; `spiffex check`
warns about it. A state that uses `x509.cn` is refused by a 0.2.0 issuer.

## Getting SVIDs

**From the agent.** The agent serves the X.509-SVID profile of the Workload API next to the JWT one
whenever its issuer has a CA. `FetchX509SVID` streams the workload's chain, a PKCS#8 private key the
agent made in memory for that certificate, and the trust domain's bundle. It renews at a random
40 to 50 percent of the lifetime and sends each renewal to every open stream. It retries with
backoff while the issuer is down and never sends a certificate with less than a tenth of its life
left. Without a CA at the issuer, both X.509 calls answer `Unimplemented`. See
[X.509-SVIDs from the agent](configuration.md#x509-svids-from-the-agent) for the details.

Go, with go-spiffe, a server that accepts only workloads of its own trust domain and a client that
accepts only the server it means to call:

```go
source, err := workloadapi.NewX509Source(ctx) // SPIFFE_ENDPOINT_SOCKET names the agent
if err != nil {
	return err
}
defer source.Close()

td := spiffeid.RequireTrustDomainFromString("example.org")
serverTLS := tlsconfig.MTLSServerConfig(source, source, tlsconfig.AuthorizeMemberOf(td))

orders := spiffeid.RequireFromString("spiffe://example.org/prod/ns/shop/sa/orders")
clientTLS := tlsconfig.MTLSClientConfig(source, source, tlsconfig.AuthorizeID(orders))
```

Python, with py-spiffe. py-spiffe fetches the certificate, key and bundle but has no TLS helper and
does not verify chains, so hand them to `ssl` and check the peer's SPIFFE ID yourself:

```python
import ssl
from pathlib import Path
from cryptography.hazmat.primitives import serialization
from spiffe import X509Source

with X509Source() as source:                        # SPIFFE_ENDPOINT_SOCKET names the agent
    svid = source.get_x509_context().default_svid
    bundle = source.get_bundle_for_trust_domain(svid.spiffe_id.trust_domain)
    svid.save(Path("chain.pem"), Path("key.pem"), serialization.Encoding.PEM)

    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
    ctx.minimum_version = ssl.TLSVersion.TLSv1_3
    ctx.verify_mode = ssl.CERT_REQUIRED
    ctx.verify_flags |= ssl.VERIFY_X509_STRICT
    ctx.load_verify_locations(cadata="".join(
        c.public_bytes(serialization.Encoding.PEM).decode() for c in bundle.x509_authorities
    ))
    ctx.load_cert_chain("chain.pem", "key.pem")
    # after the handshake, read the one URI SAN of the peer certificate and compare it with the
    # SPIFFE ID you expect: nothing in `ssl` does that for you
```

`conformance/python/client.py` is a complete client and server on this pattern. Write the key file
in a private directory and remove it afterwards: it is the only place the key reaches disk.

**Without an agent: `spiffex token -x509`.** It makes a new P-256 key in memory, asks the issuer for
a certificate with the same proof flags as `spiffex token`, verifies the chain against the bundle
and writes the files:

```bash
spiffex token -issuer https://issuer.example.org -client-id vms/billing -key-file billing.key \
  -x509 -key-out svid.key -cert-out svid.crt -bundle-out bundle.crt
```

None of the three files may exist. It runs once, so something has to run it again before the
certificate expires. For a program that reads certificate files and cannot talk to the Workload API,
a tool that writes them from the agent, such as
[spiffe-helper](https://github.com/spiffe/spiffe-helper), is the usual answer; spiffex does not test
against it. A script that speaks to the token endpoint directly is in
[Asking for an X.509-SVID](configuration.md#asking-for-an-x509-svid).

## Using them with data stores

A data store authenticates a client from the certificate it presents in the TLS handshake. Both
examples below use the certificate files of the previous section. They need the trust domain's X.509
bundle as the store's client CA file; it holds the roots, not the intermediate. The store's own
server certificate is an ordinary one for its host name, because an X.509-SVID has no DNS name.

Both were run end to end with spiffex: PostgreSQL 15.19 and Valkey 9.1.2, with certificate files
from `spiffex token -x509` and from the agent through go-spiffe, under a root made by `ca init`, and
with `token -x509` files under an intermediate below an offline root. The root runs predate the
change that leaves the root out of the chain. Envoy and MariaDB were not tried.

Three things hold for both stores:

- **The bundle file is not reread by itself.** After a root is added or retired, which is rare,
  PostgreSQL needs `select pg_reload_conf()` or a SIGHUP, and Valkey needs `CONFIG SET
  tls-ca-cert-file <the same path>`. Until then a client whose chain is under the new root is
  refused (PostgreSQL says `unknown ca`).
- **The client certificate file must be the chain.** When the CA is an intermediate, the leaf alone
  is refused, because the store has the root and not the intermediate. `-cert-out` of `spiffex token
  -x509` and the agent's chain already hold what is needed: use that file as `sslcert` or as the
  client certificate.
- **Renewal replaces the certificate and the key together.** A certificate from one SVID with the
  key of another fails with "key values mismatch". Write both into a new directory and swap a
  symlink to it. Renaming the two files one after the other also works, but a connection opened
  between the renames fails once.

**PostgreSQL.** Client certificates are matched by common name, which is why the subject carries the
SPIFFE ID. In `postgresql.conf`, `ssl = on`, `ssl_cert_file` and `ssl_key_file` for the server, and
`ssl_ca_file` pointing at the bundle. In `pg_hba.conf`, a `cert` line with a map:

```text
hostssl  all  all  0.0.0.0/0  cert  map=spiffe
```

In `pg_ident.conf`, one line for each identity that may connect, naming the role it becomes:

```text
# map      system-user (the CN)                                  database role
spiffe     "spiffe://example.org/prod/ns/shop/sa/billing"        billing_app
```

The client connects with `sslmode=verify-full`, `sslrootcert` (the server's CA), `sslcert` and
`sslkey`, and with `user=billing_app`, the role the map names: without it libpq sends the operating
system user name, and PostgreSQL refuses it with "no match in usermap". The map is per role, so a
certificate cannot become a role it has no line for, `postgres` included.

An identity longer than 64 characters has no CN, so PostgreSQL refuses it (from its source it logs
"client certificate contains no user name"; this was not run). That is deliberate: keep the IDs of
workloads that use PostgreSQL short, or choose a shorter CN with `x509.cn`, below. Do not switch to
`clientname=DN`: without the CN, the subjects of all long identities are the same, and a map line
for one would admit every other.

**Longer identities, with `x509.cn`.** Set the CN of the origin that serves PostgreSQL clients to
the path without its leading `/` (a CN must not start with one, see above), which drops `spiffe://`
and the trust domain, and map that:

```yaml
origins:
  tenants:
    provider: kubernetes
    prefix: /tenants
    name: "{kubernetes.io/namespace}/backend"
    x509: { cn: "{path|trim_prefix:/}" }
```

```text
# map      system-user (the CN)                          database role
spiffe     "tenants/kokkenogco/backend"                  kokkenogco_backend
```

That leaves 64 characters for `tenants/<tenant>/backend`, 48 for the tenant name. For longer paths,
or to keep names out of the map, use a hash, which is always the same length:
`x509: { cn: "{path|hash:24}" }`. The map then holds the hash of the path, which is computed from the
SPIFFE ID the same way the issuer does it:

```sh
printf %s /tenants/kokkenogco/backend | openssl dgst -sha256 -binary | base32 -w0 | tr A-Z a-z | tr -d = | cut -c1-24
# ufprsusxu3qhzkgyalgz55d5
```

```text
spiffe     "ufprsusxu3qhzkgyalgz55d5"                    kokkenogco_backend
```

Hash the path (the placeholder before `|hash`), not the SPIFFE ID, if the map is to be written
without knowing the trust domain; with `{spiffe_id|hash:24}` the trust domain is part of the input.
24 characters are 120 bits; the least allowed is 24. A CN longer than 64 characters, or a
trim that does not apply, fails the request, so a role can never be reached by a name that was
shortened.

libpq rereads the files for each new connection, so renewal needs only rewritten files. The key must
be mode 0600 or 0400 when the client owns it; libpq 18 (the version tested) also accepts a
root-owned file of mode 0640, which suits a Kubernetes Secret volume with `fsGroup`, but do not
count on that with other libpq versions. PostgreSQL checks the client certificate only when the
connection opens, so a session that is open keeps running after the certificate is rotated or has
expired.

**Valkey 9.1.** `tls-auth-clients-user URI` makes Valkey take the SPIFFE ID from the URI SAN and
look for an ACL user with that exact name, which has no length limit. The first URI in the
certificate that names an enabled user wins:

```text
tls-port 6379
tls-cert-file /etc/valkey/server.crt
tls-key-file /etc/valkey/server.key
tls-ca-cert-file /etc/valkey/spiffe-bundle.pem
tls-auth-clients yes
tls-auth-clients-user URI

user default off
user spiffe://example.org/prod/ns/shop/sa/billing on ~orders:* +@read +@write
```

Turn the `default` user off. A certificate that matches no user still completes the TLS handshake
and leaves the client as `default`; with `default off`, every command except `AUTH` then answers
`NOAUTH`. The match is made once, when the connection opens, so a renewed certificate takes effect
on the next connection and open connections keep their identity. Valkey 9.0 has only `CN`, which
works with SPIFFE IDs of up to 64 characters.

**Do not give these users `nopass`.** A user with no password and no `nopass` logs in by certificate
alone, and `AUTH` for it answers `WRONGPASS`. With `nopass`, anyone holding any valid SVID, even one
that maps to no user, can send `AUTH <user> anything` and become that user.

Valkey 7 and later give a new user no pub/sub channels (`resetchannels`). Clients that use them,
such as a Celery result backend (tested) or a worker, whose events and control messages also use
them (not tested), need `&*` or the channel patterns they use added to the user.

## What is tested

The conformance matrix (`conformance/run.sh`, results in
[CONTRIBUTING.md](../CONTRIBUTING.md#the-interoperability-contract)) gets an SVID for one workload
six ways: through go-spiffe and py-spiffe over the Workload API, through `spiffex token -x509`, and
by CSR for P-384, Ed25519 and RSA-2048 keys. Each one has to be accepted by go-spiffe's chain
verification, a go-spiffe mTLS server and client, and a Python `ssl` server and client, the four
mTLS ones also in a form that trusts both trust domains' CAs, which makes nine verifiers and 54
pairs, all accepted. The same verifiers must refuse the SVID of an issuer in another trust domain
(54 pairs, all refused), once because the chain does not verify and once, with both CAs trusted,
because the SPIFFE ID is not of the right trust domain, and a server must refuse a client without a
certificate. Unit tests also verify leaves of each key type with `openssl verify -x509_strict`, and
the kind test runs mTLS between two pods with identities from the cluster origin.

Not tested, so treat them as unknown:

- **rustls-webpki, BoringSSL and Java.** They are the other implementations that matter for the CA's
  name constraints (critical, URI and DNS subtrees only). A verifier that mishandles them either
  rejects every SVID or ignores the fence. Go and OpenSSL enforce them; the others have not been
  tried.
- **A CA that is an intermediate under a root, in the matrix.** The matrix uses a root made by `ca
  init`. Intermediates are covered by the CA package's tests and Go's chain verification, not by a
  run through the other verifiers.
- **Envoy and MariaDB**, and spiffe-helper. PostgreSQL and Valkey were run by hand, as above, and
  are not part of the matrix or of CI.
- **The kind test in CI.** It runs locally, like the other end-to-end tests.

## Crypto agility

The CA is P-256 today because P-256 is the key every verifier reads, in every language and every
database driver, and a root that some consumer cannot parse breaks all of them at once. Nothing in
the leaf path assumes it, though. `ca csr` already takes P-384 and RSA, an imported intermediate may
use either, and Go chooses the signature algorithm from the CA's key.

The leaf types follow what workloads and libraries generate. The agent makes P-256, which is fast
and small and accepted everywhere; P-384, Ed25519 and RSA of 2048 to 4096 bits are accepted from a
CSR for the software that has to use them. RSA-PSS is not used anywhere, since support for it in
certificates is patchy. A new leaf type is a line in the issuer's allow-list and a row in the spec.

A post-quantum CA, say ML-DSA, would arrive as an ordinary rotation. Add the new CA as a second
anchor, let it wait out `activation_delay` in the bundle, and the issuer signs with the newest
active CA from then on, with the old one retained until what it signed has expired. What it needs
first is support in Go's `crypto/x509` to parse, create and verify such certificates, which the
issuer's leaf path and the probe it signs on load both rely on, and a check that the verifiers
listed above can read the new root. A verifier that cannot parse an anchor fails on the whole
bundle, so the first step would be an opt-in, and the rotation rules already allow two anchors at
once, which is what a parallel or hybrid period needs. None of this is built.

## Compared with SPIRE

- **Revoking the last JWT key.** In SPIRE (1.9 and later, `spire-server localauthority`) an
  authority is retired in four steps (prepare, activate, taint, revoke), and revoking needs a
  replacement to be active first. spiffex lets you remove the last key, and stops signing JWT-SVIDs
  until another arrives. That is deliberate. It is an emergency stop for a leaked key, where an
  issuer signing with an unsafe key is worse than a quiet one, and it is the same as removing the
  last CA key. The cost is an outage for JWT-SVIDs. Add the replacement first if you can.
- **No taint signal yet.** SPIRE can mark a key as tainted, and agents then replace the SVIDs it
  signed before it is revoked. spiffex agents learn of a removal when the key leaves the bundle, and
  then drop the cached JWT-SVIDs it signed. A signal ahead of the removal is planned as a follow-up.
- **Agents hold SVIDs in memory.** The agent's cache is memory only: a restart fetches new ones, and
  the private keys of X.509-SVIDs are made in memory and written nowhere. The memory is not locked
  and cannot be zeroed from Go, so use encrypted swap where a key reaching swap matters.
- **One agent serves one workload.** There is no node agent and no workload attestation; the agent
  proves its workload with the key or token it is given. The agent's socket is the boundary, so keep
  it private to the workload.
